3. THE 6-STAGE PIPELINE (CORE SYSTEM)
================================================================================

STAGE 1: WORLD MODEL RECONSTRUCTION (Language Understanding)
  Purpose: Extract semantic understanding from teacher's natural language request
  Input:   "Create a fractions module for 3rd graders"
  Output:  Domain model (JSONB):
    - Concepts: Fraction, Numerator, Denominator, Part, Whole
    - Operations: Add, Subtract, Simplify, Visualize
    - Relationships: Fraction HAS Numerator, Fraction HAS Denominator
    - Progression: visualization → understanding → arithmetic
  Status:  NOT IMPLEMENTED

STAGE 2: RULE GENERATION ENGINE (Business Logic)
  Purpose: Convert domain understanding into executable rules
  Input:   World model from Stage 1
  Output:  Executable rules:
    - Validation: denominator != 0
    - Calculation: add_fractions((a/b), (c/d)) = (ad+bc)/(bd)
    - Progression: master visualization before arithmetic
    - Feedback: show hints when incorrect
  Plus:    Python/JavaScript code + unit tests
  Status:  NOT IMPLEMENTED

STAGE 3: DATA MANAGEMENT (Database Design)
  Purpose: Design PostgreSQL schemas and prepare data
  Input:   Rules from Stage 2
  Output:  - Normalized schemas (3NF)
           - Migration scripts
           - Pseudo data (if real data unavailable)
           - Index definitions
  Example: fraction_problems, student_attempts, student_progress tables
  Status:  NOT IMPLEMENTED

STAGE 4: INPUT STRATEGY DESIGN (Data Collection)
  Purpose: Determine how students will provide input
  Input:   Data schema from Stage 3
  Output:  - Input method specs (forms, drag-drop, tracking)
           - Validation rules
           - Data flow diagram
           - UX interaction patterns
  Status:  NOT IMPLEMENTED

STAGE 5: UI AUTO-GENERATION (React Components)
  Purpose: Generate complete React components for student/teacher interaction
  Input:   Input strategy from Stage 4
  Output:  - React components (TypeScript JSX)
           - Styling (KAIST brand)
           - Accessibility (WCAG 2.1 AA)
           - Responsive design (mobile/tablet/desktop)
  Example: FractionVisualizer, ProblemForm, ProgressBar
  Status:  NOT IMPLEMENTED

STAGE 6: INTEGRATION & DEPLOYMENT (Production Ready)
  Purpose: Create complete, production-ready, deployable system
  Input:   UI components from Stage 5
  Output:  - API endpoints (Express/FastAPI)
           - Integration tests
           - Docker container
           - Documentation (API, user guides, tech docs)
           - Monitoring config (Prometheus/Grafana)
  Status:  NOT IMPLEMENTED

Pipeline Performance:
  - Simple module:   2-5 minutes end-to-end
  - Medium module:   5-15 minutes
  - Complex module:  15-30 minutes
  Target: <2 hours total (including teacher review)

4. DATABASE SCHEMA (PLANNED)
================================================================================

Core System Tables (PostgreSQL):

  modules
    ├── id (UUID)
    ├── name, description
    ├── teacher_id (FK)
    ├── status (generating|active|archived)
    ├── world_model (JSONB)       ← Output from Stage 1
    ├── generated_schema (JSONB)   ← Schema specification
    ├── generated_ui (JSONB)       ← UI definitions
    └── version (integer)

  teachers
    ├── id (UUID)
    ├── name, email (unique)
    ├── institution
    ├── role (teacher|admin|maintainer)
    └── preferences (JSONB)

  students
    ├── id (UUID)
    ├── name, grade_level
    └── enrolled_modules (array)

  generation_jobs
    ├── id (UUID)
    ├── module_id (FK)
    ├── stage (1-6)
    ├── status (pending|in_progress|completed|failed)
    ├── input_data, output_data (JSONB)
    ├── error_log
    └── started_at, completed_at

  rules
    ├── id (UUID)
    ├── module_id (FK)
    ├── name, type (validation|calculation|progression|feedback)
    ├── complexity_score
    ├── is_ontology (boolean)
    ├── code (generated)
    └── ontology_reference

  dynamic_schemas
    ├── id (UUID)
    ├── module_id (FK)
    ├── table_name
    ├── schema_definition (JSONB)
    ├── migration_script
    └── is_applied (boolean)

Dynamically Generated Tables (per module):
  - {module_name}_problems       (exercise data)
  - {module_name}_attempts       (student submissions)
  - {module_name}_progress       (learning progress)

Example for Fractions Module:
  fraction_problems:
    ├── id, module_id, problem_type
    ├── numerator_1, denominator_1
    ├── numerator_2, denominator_2 (if needed)
    ├── visual_representation, difficulty_level
    └── correct_answer_numerator, correct_answer_denominator

  fraction_attempts:
    ├── id, student_id, problem_id
    ├── answer_numerator, answer_denominator
    ├── is_correct, time_spent_seconds
    └── attempted_at
